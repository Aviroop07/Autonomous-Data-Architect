PROBLEM STATEMENT

The Finalized Assignment

One problem statement, given to the whole class. Each group of 3-4 students receives its own schema + natural-language description -- same task, different instance.

1Constraints & Triggers

Given

A relational schema + the natural-language description it was built from.

Task

Identify the business-rule constraints implied by the description that the schema's FKs/PKs do not enforce on their own, and write the CHECK constraints / triggers that enforce them.

2Constraint-Exercising Test Data

Task

Write INSERT/DELETE/UPDATE sequences that explicitly demonstrate each constraint from Part 1 both firing (rejecting a violation) and passing (accepting valid data) -- i.e. the student's own proof that their triggers actually work.

3Distributional Constraint Verification

Given

Distributional claims stated in the description (e.g. "80% of loans are under $50k", "credit score correlates with approval").

Task

Write analytic SQL (window functions, percentile_cont, grouped correlation checks) that verifies whether a supplied dataset actually satisfies these claims.

CHALLENGE 1 OF 3

Instructor Workload

  • The bottleneck is not writing the assignment text -- it's producing one distinct (schema, description) pair per group, each rich enough to have real semantic constraints and at least one non-trivial distributional claim.
  • Manually authored, this is 2-4 hours per pair with care; for 30-40 groups that is 60-150 hours of prep -- unrealistic inside a one-month course timeline.
  • Every auto-generated pair still needs a manual sanity pass: an ambiguous or ungradeable constraint costs time at grading, which is worse than costing time at authoring.
  • A fixed "difficulty envelope" (schema size, constraint count, number of distributional claims) has to be set once so groups get comparably-sized problems, not tuned per group.
  • Grading itself is recurring workload: each group's triggers, test sequences, and analytic SQL need to be run and checked, not just read.
CHALLENGE 2 OF 3

Student Difficulty

  • Constraints/triggers from NL -- moderate. A normal DB-course skill, but harder than usual because it is open-ended: there is no single correct constraint list to match against.
  • Test data proving violation/satisfaction -- the most pedagogically valuable part, and the part students chronically underdo, since writing thorough test cases is unglamorous compared to writing the trigger itself.
  • Distributional verification via SQL -- the hardest leg for a first-pass BTech course unless window functions and percentile queries have already landed in the syllabus by the time this is assigned.
  • Net effect: the assignment is front-loaded toward constraint-writing and back-loaded toward analytics -- sequencing inside the month matters as much as the content itself.
CHALLENGE 3 OF 3

LLM-Cheating Resistance

  • Be realistic: writing triggers/CHECK constraints from a schema + NL spec is squarely in-distribution for current LLMs. Giving each group a different schema blocks copying between groups, but not LLM-assisted solving within a group.
  • The fix is not preventing LLM use -- it's grading on something a one-shot LLM answer doesn't reliably produce:
    • Hidden mutation-test battery: the instructor holds a private set of insert/delete/update statements per problem (some should be rejected, some should pass). Grade the trigger set by how many it catches, not by reading the SQL.
    • Live oral component: pick one trigger, change one requirement on the spot, ask the student to modify it in front of the grader (~5 min/group).
    • Cross-check the test-data leg against the instructor's hidden mutations -- if a group's own test suite would not have caught cases they didn't personally author, that is a visible signal, independent of who wrote the SQL.
  • This reframes grading from "did they cheat" (unenforceable) to "does the delivered artifact demonstrably work and can the student explain it live" (enforceable).
IMPLEMENTATION PLAN

Fitting This Into a One-Month Course

Constraints: Anupam teaches SQL + database design + normalization theory to IIT Hyderabad BTech students over one month, and this assignment must run side-by-side with that coursework in the same window. Problem statements (schema + description per group) must be prepared before the month starts.

IMPLEMENTATION PLAN

Before the Month Starts

Pre-generate the per-group problem set

  • Fix the difficulty envelope first: schema size (e.g. 4-6 tables), 4-6 semantic constraints, 1-2 distributional claims per pair -- small enough that grading 30-40 groups is tractable inside the month.
  • Generate candidate (schema, description) pairs at that envelope size, then have a human pass over each one to confirm the intended constraints are unambiguous and the distributional claims are checkable from a dataset that will actually be supplied.
  • For each pair, author the hidden mutation-test battery and the "intended constraint list" answer key at the same time as the pair itself -- not later, so grading capacity is prepared alongside the problem, not improvised during the busy month.
IMPLEMENTATION PLAN

During the Month -- Sequencing Against the Syllabus

Week 1

Schema design + normalization theory taught in parallel. Assignment released but idle -- students read their group's schema/description, no deliverable due yet.

Week 2

Once constraints/triggers and basic DML are covered in lecture: Part 1 (constraints & triggers) opens. Students submit their trigger set for their group's schema.

Week 3

Once more DML and basic analytic SQL (aggregates, window functions) are covered: Part 2 (test data proving violation/satisfaction) and Part 3 (distributional verification) open together.

Week 4

Buffer week. Hidden mutation-test grading run against every group's Part 1 submission; live oral/on-the-spot-edit sessions scheduled per group; final scores reconciled.

IMPLEMENTATION PLAN

Why This Sequencing Works

  • Each part unlocks only after the SQL/normalization concept it depends on has actually been taught -- students are never asked to use a tool before lecture covers it.
  • Front-loading Part 1 (the moderate-difficulty leg) and back-loading Part 3 (the hardest, analytics-heavy leg) matches the difficulty profile identified in Challenge 2.
  • Preparing the hidden mutation battery and answer key before the month starts turns Week 4 grading into a mostly-mechanical run rather than fresh authoring under time pressure.
  • The one-time difficulty-envelope decision keeps every group's problem comparably sized, so a single hidden-mutation-battery template can be reused with per-group substitution instead of being redesigned 30-40 times.
