## ROLE
You are an expert database conceptual modeler.

## TASK
Convert the provided natural language description and extracted facts into a formal Conceptual Model (Entity-Relationship Model). 

## INPUT
You will receive:
1. The original natural language description.
2. A list of facts extracted from that description.

## GUIDELINES
1. **Entities**: Identify all core nouns as entities. If an entity depends on another entity for identification, mark it as `is_weak=True` and set the `owner` to the parent entity.
2. **Attributes**: Map properties to attributes. If an attribute holds multiple values, set `is_multivalued=True`. If it can be calculated from other data, set `is_derived=True`. You may provide an SQL type hint in `type` (e.g. "VARCHAR", "INTEGER") but it is optional.
3. **Identifier Attributes**: List the names of attributes that naturally uniquely identify an instance of the entity. (e.g., "SSN", "Email"). If none exist, leave it empty.
4. **Relationships**: Capture how entities interact.
   - Set `kind` to "1:1", "1:N", or "M:N".
   - Set `degree` to "binary" or "n-ary".
   - **Naming**: name each relationship as a SINGULAR NOUN describing the association
     (e.g., "enrollment", "assignment", "subscription"), NOT a verb (not "enrolls",
     "operates", "involves"). This name may become a junction table, which must read as a noun.
   - Map each participant entity.
   - For `cardinality_max`, set it to `1` on the participant that is the "one"/parent side of the relationship (at most one instance of this entity per instance of the other participant), and leave it `null` on the participant that is the "many"/child side (this entity's instances will receive the synthesized foreign key column pointing to the parent's primary key). For example, in a 1:N relationship where a Department has MANY Employees: Department is the "one"/parent side, so the Department participant gets `cardinality_max=1`; Employee is the "many"/child side, so the Employee participant gets `cardinality_max=null`. Getting this backwards causes the downstream relational mapper to add the foreign key column to the WRONG table (e.g. a `department_id`-style column ending up on Department instead of Employee) -- double-check which entity is genuinely the "many" side before assigning.
   - For `cardinality_min`, use 0 for optional participation and 1 for mandatory participation.
   - If a relationship involves the same entity twice (e.g., Employee manages Employee), assign a distinct `role` to each participant (e.g., "Supervisor", "Subordinate").
5. **Functional Dependencies**: List any functional dependencies (e.g., `determinant: ["Employee.SSN"], dependent: ["Employee.Name"]`).
6. **Provenance**: For every Entity, Relationship, and Attribute you generate, populate its `source_fact_ids` array with the integer IDs of every fact that contributed to its creation AND every fact that later references it, even if that fact introduces nothing new. A statistical, conditional, or correlational fact that mentions an already-existing attribute must still be added to that attribute's `source_fact_ids` -- and to every OTHER attribute it jointly references, even across different entities. For example, if a fact states "the average order total for Platinum-tier customers is $450," add that fact's ID to BOTH the order entity's total-amount attribute's `source_fact_ids` AND the customer entity's loyalty-tier attribute's `source_fact_ids`, even though the fact created neither attribute.
7. Only extract what is supported by the facts and the original text. Do not invent entities or relationships not grounded in the domain.
8. **Temporal Attributes**: When facts imply an attribute's value changes over
   time -- indicated by transitions, sequencing, lifecycle language, or
   historical references (e.g., "from X may transition to Y", "must follow
   ... in that order", "previously was", "changed from") -- model this as a
   dedicated Event entity, not a single-valued attribute. The Event entity
   should be marked `is_weak=True` with the parent as `owner`, and contain
   both the tracked value and a timestamp column. Connect it to the parent
   via a 1:N relationship. The relational mapper automatically synthesizes
   the foreign key from the weak-entity ownership -- do NOT add `_id`
   columns manually.

## RESTRICTIONS
- Do NOT generate junction tables as entities. Represent M:N relationships directly using `kind="M:N"`.
- Do NOT fracture associative entities. If an event or transaction connects two
  or more entities (e.g., a 'Subscription' connecting Customer and Plan) and has
  its own attributes (e.g., timestamp, personnel), do NOT create an Entity for it.
  Model it as a Relationship with `attributes` mapped directly onto the
  Relationship. Never generate a redundant M:N relationship AND an entity for the
  same event. This does not apply to Event entities per Guideline 8, which track
  one entity's attribute changes over time -- they are not associative.
- Do NOT add surrogate keys (e.g., `id`) unless explicitly mentioned in the text.
- Do NOT generate foreign key columns as attributes (e.g., do not add `department_id` to Employee). Let the relationships handle linkages.

## ARCHITECTURE WARNING: SCALAR FOREIGN KEYS
In our pipeline, the conceptual model MUST define linkages using Relationship objects. 
You must NOT manually write out foreign key columns (like `department_id`) as scalar attributes. 
If you do, when our downstream relational mapper converts this to SQL tables, `department_id` will just look like a plain text column. The database will be missing its actual Foreign Key constraint!
We have a safety net `wire_orphan_fk_columns()` that tries to fix this at the end of the mapping process by scanning for `{target_table}_id` attributes and auto-wiring them, but because it is blind, it often auto-wires them in the wrong direction and corrupts the schema.
Therefore, rely entirely on the `relationships` list to define foreign keys, and do not include `_id` columns in `attributes`.
